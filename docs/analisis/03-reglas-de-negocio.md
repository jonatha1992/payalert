# 03 — Reglas de negocio

Definiciones únicas de restricciones e invariantes verificadas en implementación. [Inferido] señala regla formalizada a partir de código, pendiente de aprobación funcional. Los procesos/CU enlazan a estos IDs sin reproducir la regla.

| ID | Regla | Evidencia comprobable |
|---|---|---|
| RN-01 | Aislar datos por negocio y, cuando aplica, sucursal. El identificador enviado por cliente es una petición, no autoridad; para service role debe aplicarse scope autenticado y validar pertenencia de sucursal. | `frontend/lib/server/scope.ts:37-69`; `frontend/lib/server/session.ts:10-17,55-65`; tests `frontend/tests/server/scope.test.ts`. |
| RN-02 | Aplicar permisos server-side por rol/recurso/acción; normalizar `owner→owner`, `admin→manager`, `employee→cashier`. `support` existe solo como rol de producto en RBAC, no en el enum de sesión. | `frontend/lib/server/rbac.ts:3-27`; `frontend/lib/server/scope.ts:7-75`. |
| RN-03 | No aceptar evento MP antes de verificar firma. Para Ualá v2 no asumir firma: el conector valida formato/identificador de orden y luego exige consultar la API. | `frontend/lib/payments/connectors/mercadopago.ts`; `frontend/lib/payments/connectors/uala.ts`; `frontend/lib/server/webhookHandler.ts`; `docs/providers/uala.md`. |
| RN-04 | El cuerpo del webhook es señal de recuperación, no autoridad de monto/estado. Obtener movimiento desde API del proveedor por ID; usar importe/estado recuperados. | Contrato `frontend/lib/payments/types.ts:120-131`; conectores MP/Ualá; `frontend/lib/payments/normalize.ts`. |
| RN-05 | Deduplicar eventos por proveedor + clave de dedupe en cola; deduplicar transacción por proveedor + ID externo. Repeticiones no deben volver a notificar. | `docs/migrations/010_pay14_webhook_queue.sql:1-15`; `docs/migrations/005_payments_hardening.sql:54-61`; `frontend/lib/server/webhookQueue.ts`; `frontend/lib/payments/ingest.ts`. |
| RN-06 | Matching solo evalúa cobros `WAITING`: mismo importe suma 60 (<0.005 de diferencia), moneda 10, ventana temporal 20 (desde creación menos tolerancia default 120 s hasta expiración), referencia externa exacta 10, proveedor coincidente 20. Referencia exacta al ID tiene precedencia AUTO; sin referencia, score <70 NO_MATCH, ≥70 con múltiples candidatos MANUAL_REVIEW, único candidato ≥90 AUTO y único 70–89 SUGGESTED. | `frontend/lib/payments/matching.ts:36-86`; tests `frontend/tests/payments/matching.test.ts`. |
| RN-07 | No asignar un movimiento a más de un cobro esperado: unicidad de `expected_payment_id` en movimiento y `matched_transaction_id` en cobro, más control en la ruta de resolución. | `docs/migrations/005_payments_hardening.sql:87-97`; `docs/migrations/008_pay16_match_evidence.sql:8-10`; `frontend/lib/server/expectedPayments.ts`. |
| RN-08 | Cifrar secretos de conexión antes de persistir y descifrar solo en servidor. `secretBox` reconoce formatos/versiones; migración legacy usa formato v1. La versión v2 está condicionada a clave/configuración según código; no inferir rotación operativa concluida. | `frontend/lib/payments/secretBox.ts`; `frontend/lib/server/connections.ts`; `scripts/migrate-payment-tokens.mjs`; `scripts/payment-token-migration.mjs`; `docs/migrations/005_payments_hardening.sql:23-26`. |
| RN-09 | Estado de conexión está dentro de `CONNECTED`, `DEGRADED`, `REAUTH_REQUIRED`, `DISCONNECTED`, `ERROR`; check saludable recupera CONNECTED, token inválido requiere reautenticación y fallo transitorio degrada. | `frontend/lib/payments/types.ts:12`; `frontend/lib/payments/connectionHealth.ts`; `frontend/lib/server/connections.ts`; `docs/migrations/005_payments_hardening.sql:23-24`. |
| RN-10 | Estados de cobro esperado: `WAITING`, `MATCHED`, `EXPIRED`, `MANUAL_REVIEW`, `CANCELLED`; expirar no equivale a cancelar ni a pago recibido. | `frontend/lib/payments/types.ts:14`; `docs/migrations/005_payments_hardening.sql:72-84`; `frontend/lib/server/expectedPayments.ts`. |
| RN-11 | Estados de evento de cola limitados a `PENDING`, `PROCESSING`, `DONE`, `FAILED`, `DEAD`; claims concurrentes usan `FOR UPDATE SKIP LOCKED`, respetan reintento/lock vencido. | `docs/migrations/010_pay14_webhook_queue.sql:1-46`; `frontend/lib/server/webhookQueue.ts`; `frontend/lib/server/webhookWorker.ts`. |
| RN-12 | Enlazar tenant de conexión con cuenta del proveedor; cuenta activa no se asigna a varios negocios si tiene `provider_account_id`. | `docs/migrations/005_payments_hardening.sql:34-38`; `frontend/lib/server/connections.ts`. |
| RN-13 | Antes de enviar push, filtrar suscriptores por negocio y sucursal; no incluir cuerpo de webhook/credenciales. [Inferido] Limitar datos del aviso a resumen operativo/pago seguro. | `frontend/lib/server/push.ts`; `frontend/lib/server/webhookHandler.ts`; `frontend/lib/payments/types.ts:35-36`. |

## Estados como vocabulario de dominio

Los valores de estado se definen exclusivamente en RN-09 (conexión), RN-10 (cobro esperado), RN-11 (evento de cola) y RN-16 (movimiento). El catálogo gráfico de estados vive en `04-diagramas.md` y representa esos IDs, no redefine sus transiciones.
